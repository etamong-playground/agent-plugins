# macOS 앱 개발

만들 앱의 목적과 사용할 기능을 정하고, 작은 단위로 구현하고 검증하는 가이드입니다.
먼저 사용자가 실제로 하는 작업과 불편한 점을 확인합니다.
기술과 분야별 기능은 요구사항이 구체화된 뒤 선택합니다.
스킬 설치가 필요하면 [설치와 스킬](#purpose-installation)에서 시작합니다.

## 사용할 앱의 목적부터 정하기

앱을 쓸 사람, 지금 작업하는 방법, 바꾸고 싶은 결과를 설명하면 됩니다.
처음부터 화면 구성이나 API를 정할 필요는 없습니다.
사용자의 직무는 작업을 이해하는 배경으로 전달하고, 어떤 기능이 필요한지는 별도로 확인합니다.

| 먼저 확인할 내용 | 정리할 결과 |
| --- | --- |
| 누가 언제 앱을 사용하는지 확인합니다. | 실제 사용 상황과 해결할 문제를 정합니다. |
| 지금 어떤 순서로 작업하는지 확인합니다. | 앱에서 완성할 사용자 작업 하나를 고릅니다. |
| 어떤 정보를 받고 어떤 결과를 남기는지 확인합니다. | 입력, 출력과 저장할 데이터를 정합니다. |
| 무엇이 되면 성공인지 확인합니다. | 실행해서 확인할 수 있는 완료 조건을 만듭니다. |
| 어떤 환경과 제약이 있는지 확인합니다. | 지원할 Mac 환경과 필요한 연동 범위를 정합니다. |

답이 정해지지 않은 항목은 질문으로 남깁니다.
예시에서 나온 기능을 그대로 첫 버전의 요구사항으로 확정하지 않습니다.

## 인터뷰부터 검증까지

프로젝트의 진행 상태에 맞는 단계부터 시작합니다.
이미 기획서나 코드가 있다면 기존 결정을 확인한 뒤 이번 작업의 범위를 정합니다.

<!-- workflow-diagram -->

| 관점 | 사용할 스킬 | 확인할 결과 |
| --- | --- | --- |
| 기획서 인터뷰 | grilling, platform-plan-doc | 사용자 작업과 첫 버전의 범위, 완료 조건을 정리합니다. |
| 요구사항 피드백 | requirements-feedback | 현재 동작과 원하는 결과를 비교하고 변경할 요구사항을 정합니다. |
| Mac 앱 설계 | macos-app-development, codebase-design | 요구사항과 기존 코드에 맞는 앱 구조와 기술을 선택합니다. |
| 화면과 동작 비교 | prototype, macos-ui-review | 화면 후보와 실제 Mac 조작 방식을 확인합니다. |
| 테스트부터 구현 | tdd | 확정한 동작 하나의 기대 결과와 실패 조건부터 테스트합니다. |
| 오류와 성능 검증 | diagnosing-bugs, optimize-memory | 재현 조건과 측정 근거로 문제를 확인합니다. |
| 구현과 문서 리뷰 | adversarial-review, audience-review | 요구사항, 동작, UI와 설명을 여러 관점에서 확인합니다. |

## 기획서 인터뷰 요청하기

현재 상황을 설명하고, 중요한 질문부터 받습니다.
기능을 정하기 전에 에이전트가 특정 종류의 앱을 선택하지 않도록 작업 목적부터 확인합니다.

```text
onul의 grilling과 platform-plan-doc을 사용해 줘.
Mac에서 사용할 앱을 만들고 싶어. 아직 기능은 확정하지 않았어.
내가 현재 어떻게 작업하고 무엇이 불편한지부터 질문해 줘.
사용자, 작업 순서, 입력과 결과, 첫 버전의 완료 조건을 함께 정하자.
기술이나 특정 분야의 기능은 필요가 확인된 뒤 제안해 줘.
질문은 한 번에 이해할 수 있는 분량으로 해 줘.
이번에는 기획서까지만 작성하고 코드는 수정하지 마.
설명과 기획서는 한국어로 작성해 줘.
```

기획서에는 확인된 요구사항과 미정인 항목을 구분해서 남깁니다.
"빠르게 동작한다"처럼 판단하기 어려운 조건은 대상 작업과 입력 규모, 실행 환경, 허용 시간을 정한 뒤 측정합니다.

## 피드백을 요구사항으로 바꾸기

화면이나 동작에 대한 의견은 사용자가 하려는 작업과 연결해서 정리합니다.
원래 완료 조건을 만족하지 못하는 결함인지, 새로운 기능을 요청하는 것인지 먼저 구분합니다.

```text
onul의 requirements-feedback을 사용해 줘.
기획서와 현재 구현을 확인하고 내가 전달할 피드백을 정리해 줘.
현재 동작, 사용자가 해야 하는 판단, 원하는 결과, 검증할 예시를 연결해 줘.
의미가 불분명한 의견은 추측해서 요구사항으로 확정하지 말고 질문해 줘.
기존 범위가 달라진다면 어떤 결정이 필요한지 알려 줘.
이번에는 변경안까지만 작성해 줘.
```

변경이 확정되면 기획서와 완료 조건을 함께 수정합니다.
구현까지 원한다면 수정할 범위와 검증할 동작을 이어서 지정합니다.

## 개발 환경 준비

기존 프로젝트가 있다면 언어와 framework, 지원 macOS, 빌드와 테스트 명령을 먼저 확인합니다.
새 프로젝트라면 요구사항과 필요한 OS 기능을 확인한 뒤 기술을 선택합니다.
SwiftUI와 AppKit 같은 Native UI나 다른 앱 framework 중 무엇이 맞는지는 이 조건에 따라 달라집니다.

SwiftUI와 AppKit 앱 target을 개발할 때는 Mac과 [Xcode](https://developer.apple.com/xcode/)를 준비합니다.
Mac 터미널에서 `xcodebuild -version`으로 선택된 Xcode 버전을 확인할 수 있습니다.
Command Line Tools만 설치된 환경을 전체 Xcode가 필요한 앱 빌드와 Native UI 검증 환경으로 취급하지 않습니다.
다른 framework를 쓰는 프로젝트는 해당 프로젝트의 빌드 도구와 실행 절차를 따릅니다.

## TDD로 작은 기능 완성하기

TDD는 기대 동작을 테스트로 먼저 정하고, 실패를 확인한 뒤 구현하는 방식입니다.
확정한 사용자 작업에서 핵심 동작 하나를 고르고 정상 입력, 경계와 실패 조건을 정합니다.

```text
onul의 macos-app-development와 tdd를 사용해 줘.
확정한 기획서에서 이번에 구현할 핵심 동작 하나를 골라 범위를 확인해 줘.
현재 프로젝트의 언어와 구조를 유지해 줘.
기대 결과를 구현 코드와 별도로 판단할 수 있는 테스트부터 작성하자.
테스트 하나의 실패를 확인하고 최소한의 구현을 한 뒤 정리해 줘.
UI와 외부 연동이 필요한 검증은 순수 로직 테스트와 구분해 줘.
실행한 명령과 결과, 아직 확인하지 못한 항목을 알려 줘.
```

작은 동작이 확인되면 화면 상태, 저장과 연동처럼 실제 작업에 필요한 부분을 연결합니다.
테스트 방식은 선택한 기술과 target에 맞춥니다.
Native 앱에서는 Swift Testing과 XCTest의 역할을 구분하고, UI 자동화에는 XCTest와 XCUIAutomation을 사용할 수 있습니다.
지원 범위는 [Apple의 테스트 target 설명](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project)에서 확인합니다.

## 무엇을 자동으로 검증할 수 있나

| 검증 대상 | 확인할 내용 | 추가로 필요한 확인 |
| --- | --- | --- |
| 핵심 로직 | 정상 입력, 경계와 오류 입력의 결과를 비교합니다. | 기대 결과가 요구사항과 맞는지 확인합니다. |
| 저장과 외부 연동 | 저장, 재시작, 실패와 재시도 조건을 확인합니다. | 실제 권한과 대상 환경에서 확인합니다. |
| 화면과 사용자 흐름 | 주요 작업과 오류 복구를 자동화합니다. | 실제 앱의 키보드와 접근성 정보를 확인합니다. |
| 성능과 메모리 | 정한 작업과 입력 규모로 측정합니다. | 지원할 Mac과 실제 사용 조건에서 비교합니다. |
| 설치와 OS 기능 | 지원하는 배포본의 시작과 기본 동작을 확인합니다. | 최종 서명, 권한과 설치 환경을 확인합니다. |

단위 테스트, 앱 실행과 사용자 검증은 서로 다른 근거입니다.
빌드가 성공해도 사용자가 원하는 작업을 마쳤는지는 실제 흐름으로 확인해야 합니다.
실행 환경이 없는 항목은 통과로 처리하지 않고 미검증으로 남깁니다.

## Mac 화면 검토하기

확정한 사용자 작업을 실제 앱에서 수행하며 화면을 검토합니다.
정보를 입력하고 결과를 확인하는 방법, 작업 상태와 오류 복구를 이해할 수 있어야 합니다.

```text
onul의 macos-ui-review를 사용해 줘.
기획서에 있는 주요 사용자 작업을 기준으로 현재 Mac 화면을 검토해 줘.
메뉴와 단축키, focus 이동, 창 크기 변경, light와 dark appearance도 확인해 줘.
상태와 오류는 색만으로 구분하지 말고 필요한 값을 읽을 수 있게 해 줘.
VoiceOver와 키보드 조작은 실제 Native UI에서 확인해 줘.
실행 환경이 없다면 코드와 설계에서 확인한 내용, 직접 실행해야 할 절차를 구분해 줘.
```

`macos-ui-review`는 SwiftUI와 AppKit 화면을 위한 스킬입니다.
다른 UI 기술을 쓰면 그 기술에 맞는 자동화와 함께 macOS 창, 메뉴, 키보드 동작을 확인합니다.
브라우저 mockup은 구성을 비교하는 데 쓰고, 실제 Mac 앱의 동작을 검증한 결과로 사용하지 않습니다.
[macOS 디자인](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos), [키보드](https://developer.apple.com/design/human-interface-guidelines/keyboards), [접근성](https://developer.apple.com/design/human-interface-guidelines/accessibility) 설명도 참고합니다.

## 필요한 분야 기능 선택하기

추가 기능은 사용자가 필요를 설명하고 범위와 완료 조건을 정한 뒤 구현합니다.
오디오를 실제로 처리하거나 입출력해야 한다고 정했다면 `macos-audio-app`과 `audio-validation`을 선택할 수 있습니다.
이 두 스킬은 일반 Mac 앱 개발을 시작하기 위한 필수 단계가 아닙니다.
다른 전문 기능도 해당 기능의 데이터, 권한과 검증 방법을 따로 정합니다.

## 앱 배포와 설치 확인

앱을 사용할 사람과 전달할 방법을 정한 뒤 지원 macOS와 CPU, 설치와 업데이트 절차를 확인합니다.
Developer ID로 배포할 앱과 Mac App Store에 제출할 앱의 절차는 구분합니다.
[Code signing과 notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) 요건을 선택한 배포 방식에 맞춰 확인합니다.
최종 배포본을 실제 대상 환경에 설치하고 주요 사용자 작업을 다시 확인합니다.

## 에이전트에게 작업을 맡기는 기준

1. 만들 앱의 목적과 현재 작업 방법을 설명합니다.
2. 요구사항과 완료 조건을 확인한 뒤 작은 동작 하나를 구현합니다.
3. 실행한 검사와 실제 결과를 확인하고 실패한 사례를 다음 검증에 추가합니다.
4. 피드백과 독립 리뷰에서 확인한 내용을 반영하고 같은 조건으로 다시 검증합니다.
5. 확정한 분야 기능과 배포 방식에 필요한 검증을 추가합니다.

모든 스킬을 한 번에 실행할 필요는 없습니다.
현재 작업에 필요한 스킬을 선택하고, 사용자 결정이 필요한 항목과 에이전트가 직접 확인할 항목을 구분하면 됩니다.
